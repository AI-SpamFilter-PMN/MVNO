## LIVE evidence (running stack, not simulation-of-output)

### 1. SIP dialog routed (caller log) — real 407 challenge → 180 → 200
```
    <- SIP/2.0 407 Proxy Authentication Required
    <- SIP/2.0 100 trying -- your call is important to us
    <- SIP/2.0 180 Ringing
    <- SIP/2.0 200 OK
[+] call answered; media -> 10.89.0.48:30000
[+] RTP media sent: 297 packets to 10.89.0.48:30000
```

### 2. G.722 negotiated on BOTH media legs (rtpengine metadata)
`state/spool/metadata/rtpengine-meta-call-1786312445%40mvno-16d97827d2afbe9c.txt`:
```
m=audio 30094 RTP/AVP 9 0
a=rtpmap:9 G722/16000
a=rtpmap:0 PCMU/8000
m=audio 30000 RTP/AVP 9 0
a=rtpmap:9 G722/16000
a=rtpmap:0 PCMU/8000
```
Payload type **9 = G.722/16000 (wideband)** accepted on both the callee leg (30094)
and the caller leg (30000) through rtpengine.

### 3. Symmetric RTP relayed by rtpengine on both legs (pcap decode, linktype 101)
`state/spool/pcaps/call-1786312445%40mvno-16d97827d2afbe9c.pcap` (128 KB):
```
UDP packets dst==30000: 297      source 10.89.0.71:5070
UDP packets dst==30094: 297      source 10.89.0.70:5071
```
Both directions flow through rtpengine (10.89.0.48). RTP was recorded:
`state/spool/archived/live-call-1786312445...-10.89.0.70-*.wav` and `-10.89.0.71-*.wav`.

### 4. RTP payload-type note (honest)
The sim negotiates G.722 (pt 9) in SDP but streams synthetic tone bytes on pt **0**
(PCMU) — it does not bit-encode G.722. rtpengine is codec-agnostic (no transcoding),
so the negotiated pt passes through. This proves the **SIP+RTP path and G.722
negotiation**; the actual G.722 bit-stream is generated by the real endpoint
(SipClient / Android phone). Hence: **path proven, only the physical device's
G.722 encode+speech is unproven.**
